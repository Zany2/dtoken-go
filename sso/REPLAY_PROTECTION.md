# SSO signed communication and replay protection

`ReplayProtection` adds a clock window, one-time nonces, and operation binding to SSO HTTP traffic. It covers authorization, Ticket/Code exchange, introspection and userinfo for all four credential modes, revocation, center logout, and client logout callbacks. Opt in through `HTTPOptions.ReplayProtection` and `ClientConfig.ReplayProtection`. The default `nil` preserves existing protocol behavior; existing `Signer` methods remain unchanged.

## Configuration

Add the following to your existing client registration, login resolver, signing keys, and HTTP configuration. Here `serverOptions` is `sso.HTTPOptions`, `clientConfig` is `sso.ClientConfig`, and `centerStore` / `clientStore` are application-initialized `contract.Storage` instances. For separate deployments, create each component in its respective process.

```go
centerReplay, err := sso.NewReplayProtection(sso.ReplayProtectionOptions{
    Storage: centerStore,
    KeyPrefix: "company:sso:center:replay:",
    MaxAge: 5 * time.Minute,
})
if err != nil {
    return err
}
serverOptions.CheckSign = true
serverOptions.ReplayProtection = centerReplay
handler := sso.NewHTTPServer(server, serverOptions)

clientReplay, err := sso.NewReplayProtection(sso.ReplayProtectionOptions{
    Storage: clientStore,
    KeyPrefix: "company:sso:app-a:replay:",
    MaxAge: 5 * time.Minute,
})
if err != nil {
    return err
}
clientConfig.CheckSign = true
clientConfig.ReplayProtection = clientReplay
app := sso.NewClientApp(clientConfig)
```

Register `handler.Handler()` on the center and `app.LogoutCallbackHandler(...)` on the client callback route. Gin and other integrations use these settings through the same standard HTTP protocol layer.

- Enable `CheckSign` and configure matching signing keys. The center prefers registered `Client.SecretKey`, falling back to `ServerOptions.SecretKey`. The application's `ClientConfig.SecretKey` must match. Continue configuring `ClientSecret` according to the existing credential exchange rules.
- Protected requests require an explicit single `client` value, and applications must set `ClientID`. Anonymous compatibility also requires explicitly sending a registered `ClientAnonymous`.
- Storage is borrowed: the component neither creates default storage nor closes caller-owned storage. Zero `MaxAge` means five minutes; negative values or values that cannot safely be doubled return a configuration error.
- All replicas of a center must share storage, prefix, and clock window; the same applies to replicas of each application. Use distinct prefixes for separate centers or environments and keep clocks synchronized.
- Storage implementing `contract.AtomicStorage` uses `SetIfAbsent`; existing Redis storage supports it. Ordinary storage uses `Get` / `Set` with an instance-local mutex. Share one protection object within a process; this fallback does not guarantee concurrent deduplication across processes or protection instances.
- Memory storage is suitable for local debugging and loses nonce records on restart. Production storage must retain records throughout the acceptance window.

## Protocol

Every client URL construction or request method replaces reserved metadata and signs a fresh request:

| Parameter | Rule |
| --- | --- |
| `timestamp` | UTC RFC3339Nano; must satisfy `now - MaxAge < timestamp <= now + MaxAge` |
| `nonce` | Generated by `crypto/rand.Text()`; receivers accept 16–128 ASCII letters, digits, `_`, or `-` |
| `action` | Fixed operation identifier from the table below |
| `client` | Explicit client identity included in the signature and deduplication namespace |

All four fields must have exactly one nonempty value. `ParamNames.Action`, `Timestamp`, `Nonce`, and other parameter names are customizable. Protected mode requires distinct normalized protocol parameter names.

| Endpoint | action |
| --- | --- |
| authorize | `sso.authorize` |
| token | `sso.token` |
| introspect | `sso.introspect` |
| userinfo | `sso.userinfo` |
| revoke | `sso.revoke` |
| logout | `sso.logout` |
| Client logout callback | `sso.logout_callback` |

Custom URL paths do not change operation identifiers. Receivers verify signatures first, then validate metadata and claim the nonce before business effects. Invalid signatures or operations do not claim nonces. Keys hash an encoded `(client, action, nonce)` tuple, excluding the timestamp. Records remain for `2 * MaxAge` to cover accepted future clock skew.

Expired or replayed requests return HTTP 401; missing, duplicate, or incorrect operation metadata returns 400. Configuration and storage failures return 500 without bypassing protection. Direct callback verification supports `errors.Is` with `ErrRequestExpired`, `ErrRequestReplayed`, `ErrReplayProtectionConfig`, and `ErrStorageUnavailable`.

## Login round trips and retries

An unauthenticated authorization visit validates the signature and timestamp without claiming the nonce. After login, the original URL can be used once: the center claims its nonce before credential issuance and `AuthorizationExtra`. Reusing it is rejected. If login exceeds the clock window, restart authorization from the application. Protected authorization URLs must not be cached as permanent login entry points.

Other requests claim the nonce before business processing; business failures do not roll it back. Call `AuthURL`, `SignoutURL`, `ExchangeCredential`, `Introspect`, `UserInfo`, or `Revoke` again to generate a new request. Replaying a cached URL or body still fails. A fresh nonce cannot restore a consumed Ticket/Code; restart login if its exchange response was lost.

Each center callback delivery creates a fresh nonce. If the client callback handler fails, that exact signed callback cannot execute again, while a newly generated center notification can. Logout handlers should remain idempotent. With protection enabled, callback freshness uses `ReplayProtectionOptions.MaxAge`; legacy `LogoutCallbackMaxAge` only governs unprotected callbacks.

## Migration and verification

Upgrade the center and all applications first, then coordinate enabling both sides. Protected receivers reject legacy requests: enabling only the center rejects old application requests; enabling only applications rejects old center callbacks. There is no automatic downgrade or compatibility bypass. Keys, parameter names, and operation identifiers belong to the DToken-Go protocol; Sa-Token signed requests are not wire-compatible.

`replay_test.go` and `replay_http_test.go` provide regression coverage for metadata boundaries, storage faults, concurrent claims, all credential modes, login round trips, operation isolation, and callback retries. See the [testing guide](./TESTING.md) for execution instructions.
