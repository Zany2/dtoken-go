# Memory 完整工作负载验收

2026-11-26，继续执行用户已授权的 Memory 基准。全部 120 个现有 Auth 场景各运行 300 ms、重复 3 次，共 360 个样本通过；另将 4 个并发读写场景在 GOMAXPROCS=1 和 8 下各重复 3 次，共 24 个样本通过。本轮未修改生产代码或基准实现，未连接 Redis，未执行部署迁移。

环境沿用[前序测量记录](2026-11-26-memory-report_zh.md)：Go 1.27.0、Windows/amd64、AMD Ryzen 7 7840HS；全矩阵使用 GOMAXPROCS=4。工作区基于 `fff8fe862d73c4a322d82062e12f9d148032ef05` 加未提交改动。两条测量命令依次执行，避免相互争用；没有同时运行项目回归。

## 基础校验与 Provider

18 组 `IsLogin`／`CheckLogin` 中位耗时为 260.1—289.0 ns/op，均为 224 B/op、2 次分配。覆盖 1／100／1000 个终端、0／1 KiB／64 KiB Extra，关闭活跃超时和自动续期。有限／永久 TTL 校验中位数分别为 264.9／249.1 ns/op，分配相同。

权限校验耗时单位为微秒，数据为 Provider 场景；每次检查均调用一次本地 Provider。

| 终端数 | Provider 命中 | nil 回退 Session | 空列表拒绝 |
| --- | --- | --- | --- |
| 1 | 0.370 | 2.122 | 0.572 |
| 100 | 0.387 | 61.100 | 0.563 |
| 1000 | 0.390 | 597.503 | 0.583 |

命中保持 256 B/op、4 次分配，空列表拒绝保持 368 B/op、6 次分配；1000 终端的 Session 回退约 354,658 B/op、2023 次分配。命中路径不读取整个 Session，而回退路径仍承担完整 Session 解码成本。真实 Provider 的数据库／网络耗时不在此表中。

## 大 Session 仍有成本

以下写操作使用无 Extra；终端查询的主记录全部存在。单位为微秒。

| --- | --- | --- |
| 1 | 11.011 | 3.141 |
| 100 | 229.344 | 68.102 |
| 1000 | 1985.186 | 605.759 |

| 终端数 | 原始列表 | 全部存活列表 | 指定设备存活列表 |
| --- | --- | --- | --- |
| 10 | 7.115 | 14.342 | 8.627 |
| 100 | 59.891 | 129.958 | 62.573 |
| 1000 | 591.339 | 1286.522 | 601.665 |

这些接口读取或修改 Session，所以仍随终端列表大小增长。指定设备查询避免探测无关 Token，但依然解码完整 Session，不能称为常数成本。手动续期与自动维护路径不同，不能将其成本套用到普通 `CheckLogin` 的后台自动续期。

登录触发清理同样需要处理残留列表。单位为微秒，每轮在计时外恢复同一 Session 快照，计时内执行登录及清理：

| 索引条目 | 50% 主记录缺失 | 100% 主记录缺失 |
| --- | --- | --- |
| 10 | 19.779 | 17.590 |
| 100 | 115.825 | 93.360 |
| 1000 | 1083.849 | 851.709 |

缺失状态在准备阶段直接删除主记录模拟；不测量 TTL 实际到期过程。原始列表查询不写回清理，登录仅在触达名额限制时整理；这些测量没有把清理成本重新放进普通 Token 校验。

## 并发读写

下表为总墙钟耗时除以总操作数，单位 ns/op；它是吞吐对应的成本，不是每个请求的延迟或 p95/p99。并发写入的一次操作包含一次登录和一次退出。

| 场景 | GOMAXPROCS=1 | GOMAXPROCS=4 | GOMAXPROCS=8 |
| --- | --- | --- | --- |
| 同账号校验 | 319.8 | 116.7 | 92.42 |
| 多账号校验 | 320.3 | 117.2 | 91.01 |
| 同账号登录退出 | 13,981 | 19,822 | 31,086 |
| 多账号登录退出 | 13,938 | 9,589 | 14,394 |

并发校验保持 224 B/op、2 次分配。增加工作协程并不保证登录退出更快：同账号存在写协调和不同的在途终端数量，多账号也仍有共享存储、分配及调度成本。这些样本不足以确定单一竞争来源，不以本表直接决定引入存储分片或拆除账号锁。

## 收尾结论

既定主要源码改造、非联网行为回归和现有公开 Auth 的 Memory 基准矩阵已完成。这里的“完整”指上述现有 120 个场景，并非全部 API、登录策略或部署负载。没有新增失败需要修复，本轮只补齐测量记录和验收状态，不继续扩大生产架构。

真实 Redis、核心 race、实际部署持续过载与尾延迟、隔离数据迁移演练仍未完成。下一步应准备独立测试 Redis 和支持 CGO 的 C 编译器，按[验收记录](../performance-acceptance_zh.md)执行剩余验证；涉及共享存储契约的测试可能清空测试数据库，必须使用可丢弃数据。若实际负载表明大 Session 管理操作是主要瓶颈，再单独评估会话拆分、可选批量读取或针对锁竞争的剖析，并承担相应存储格式与迁移变更。
